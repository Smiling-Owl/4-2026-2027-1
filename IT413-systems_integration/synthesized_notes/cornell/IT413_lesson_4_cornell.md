# Systems Integration: Categories, Levels, and Architectures

**Date:** 2026-09-09

| Cue / Keywords | Notes |
| :--- | :--- |
| **Three Categories of Integration** | - **Web Integration:** Connects a website/web application with other applications, services, or data sources through web standards (HTTP APIs, web services) so a web channel can access or expose back-end functions.<br>- **Enterprise Application Integration (EAI):** Connects applications within the same organization (ERP, CRM, databases, legacy, supply-chain, cloud) via APIs, adapters, messaging, middleware, or an integration platform. Solves information silos.<br>- **Business-to-Business (B2B):** Connects systems/processes of independent organizations (suppliers, customers, banks, logistics) via EDI, APIs, or standards like ebXML. |
| **Scope & Category Comparison** | - Web scope: website/web app and supporting services.<br>- EAI scope: applications across departments in one enterprise.<br>- B2B scope: interorganizational network. Distinct but not mutually exclusive — a B2B transaction may enter through a web API and pass through an EAI platform. |
| **Web Drivers & Challenges** | - Drivers: online services, customer self-service, reuse of back-end functions, access via browsers/mobile clients.<br>- Challenges: API compatibility, versioning, authentication, Internet security, network latency, service availability, UX consistency. |
| **EAI Drivers & Challenges** | - Drivers: reduce duplicate data entry, automate internal work, maintain consistent information, reuse valuable legacy functions.<br>- Challenges: incompatible formats/protocols, legacy restrictions, complicated data mappings, dependencies, unclear ownership, monitoring, migration costs, middleware bottlenecks. |
| **B2B Drivers & Challenges** | - Drivers: faster order/payment cycles, lower transaction costs, fewer manual errors, supply-chain visibility, partner compliance.<br>- Challenges: agreeing on document meanings, protocols, workflows, service levels; partner onboarding, different EDI formats, identity, digital certificates, privacy, legal obligations, reliable delivery. |
| **Real-Time Integration** | Processes or transfers information with very little delay after a request/event. Commonly uses synchronous request-response (System A sends a request, waits for the response) or continuous event streams. Appropriate for current info or immediate results (checking inventory, authorizing a payment, live shipment location). Affected by network latency, service outages, traffic spikes. |
| **Asynchronous Integration** | Separates sending a message from its later processing. System A sends a command/event to a queue, topic, or message broker and continues without waiting; the broker stores the message until System B retrieves and processes it. Allows the sender/receiver to run at different times and scale independently. Useful for order fulfillment, email delivery, file processing, audit events, long-running tasks. Must handle retries, duplicate messages, ordering, correlation, monitoring, dead-letter handling, delayed completion. |
| **Real-time vs. Async** | Real-time refers to the speed at which information becomes available or receives a response; asynchronous refers to whether the sender waits for processing to finish. An asynchronous event system may still deliver and process events in near real time. |
| **Five Levels of Integration** | - **Presentation:** Combines info/interface elements from separate apps in a single view (portal); may rely on screen scraping.<br>- **Data:** Connects systems through their data — extraction, transformation, consolidation, replication, synchronization among databases/files/warehouses.<br>- **Application:** Connects systems through their functions; one app exposes an operation via an API, another invokes it during an operation.<br>- **Service:** Presents app capabilities as reusable services with defined contracts; emphasizes reuse, standard access, loose coupling.<br>- **Process:** Coordinates a complete business workflow across apps, services, departments, and partners; broadest scope. |
| **Four Integration Architectures** | - **Batch:** Collects records over time/volume, then transfers & processes as a group (scheduled jobs, bulk files, staging, ETL/ELT). Handles large volumes & runs during low use; data not immediately current; must manage failed/duplicate runs, partial processing, reconciliation.<br>- **Point-to-Point:** Direct connection between two systems with protocol, data mapping, security, and processing rules. Quick for few stable connections but tight coupling; complexity grows as more systems are added.<br>- **Broker-Based:** Intermediary (message broker, integration broker, ESB) queuing, routing, transforming, validating, enriching, and monitoring messages. Reduces direct dependencies but the broker must be operated, scaled, secured, monitored — can become a bottleneck/SPOF.<br>- **Business-Process:** Organizes interactions around a complete business outcome; a workflow/process engine coordinates services & human activities, applies rules, manages decisions/exceptions. Fits multi-step workflows but needs process ownership, modeling, governance, change management. |

---

### Summary
Systems integration can be understood through three categories — Web, EAI, and B2B — that differ mainly in scope: a web channel, applications within one enterprise, or transactions between separate organizations. Integration splits into real-time (immediate, synchronous request-response or continuous event streams) and asynchronous (the sender continues without waiting while a broker stores the message). Integration also spans five levels, from presentation (unified view) through data, application, and service (reusable contracts) up to process (whole-workflow coordination). Finally, four architectures — batch, point-to-point, broker-based, and business-process — balance trade-offs between immediacy, coupling, and complexity; broker and business-process approaches favor loose coupling and orchestration at the cost of shared infrastructure and governance.
